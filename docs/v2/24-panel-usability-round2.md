# 面板易用性第二轮诊断（U17 前置）：操作者说"呆板、无处下手、不直观"

方法：不读代码想象，而是用无头 Chrome 把线上五个页面**渲染后的结构、文案字数、按钮与输入框**逐一 dump 出来，
再对着 API 路由核实机制。下面每条都带证据。

---

## 1. 跨页面的四个根因（比任何单页问题都重要）

### 1.1 界面里混着英文枚举值——"不明确"的直接来源

面板到处是中文，但**三类最关键的词是服务器原样吐出的英文**，直接印在界面上：

| 位置 | 实测印出来的字 | 代码 |
| --- | --- | --- |
| 任务列表与详情的阶段胶囊 | `done`、`waiting`、`running`、`failed` | `panel/index.html:798,1020,1673` 直接印 `ticket.stage` |
| 记录页每条判定的结局 | `accept`、`observe`、`ignore` | `:1817` 直接印 `decision.outcome` |
| 记录页判定的原因 | `The gate admitted this request.`、`sender "stranger" is not on the list` | 服务器算好的 `reasonText`，原样显示 |
| 聊天页顶部胶囊 | `allowedSenders operator`、`disabled` | `:2326` 附近 |

**后果**：操作者要自己在脑子里做一层翻译，而"这条判定到底是受理了还是被拒了"恰恰是最不该靠翻译判断的事。
`stageClass()` 只把英文映射成**颜色**，没映射成**词**——颜色是辅助，词才是信息。

### 1.2 长段说明排在动作前面——"无处下手"的直接来源

实测每页在任何可点的东西之前要先读多少字：

| 页面 | 第一个按钮/输入框之前的说明文字 |
| --- | --- |
| **聊天** | 顶部 123 字 + 「未映射的消息」61 字 + 36 字 → **220 字**才见到频道表单 |
| **记录** | 「丢失的请求」150 字 + **209 字**（"这里没有重放按钮，因为它做不到…"）→ **359 字**，而真正的状态只有一句 22 字「没有丢失的请求」 |
| **派活** | 42 字 + 配方说明 42 字 + 附件说明 45 字 |
| **工作** | 项目 39 字 + 工作 33 字，然后**两个表单永远摊开** |

这些段落每一句单独看都是对的（它们大多是我为了"不说谎"写的：停用不等于清空、丢失不能重放、拒绝不可逆）。
**问题不是内容错，是位置错**：把"为什么"放在"做什么"前面，页面就成了一篇要先读完才能用的说明书。
正解是**倒过来**——先给状态与动作，把解释收进可展开的「为什么这么说」。

### 1.3 表单永远摊开，没有"新建"这个动作

**工作页**：项目表单（2 字段）与工作表单（4 字段）**永远摊开**，与两个列表并排，右侧还有一块
"选择左边一个项目或工作"的空详情。一页里同时有 2 个列表 + 2 个表单 + 1 个详情，**没有主次**。
**派活页（定时模式）**：排期列表下面**永远摊开**一个 7 字段的「新建排期」表单，其中"标识"还要先读 47 字规则。

对照：聊天页的频道与身份映射表单也是永远摊开——但那一页只有表单没有列表，所以问题小些。

### 1.4 只报了问题，没给下一步（这一条最伤）

**聊天页实测**：顶部胶囊写着 `disabled`，正文写着"来源已停用：频道目录里的消息不会被读取，也不会被受理"，
然后**这一页没有任何一个能启用它的控件**——开关在「设置」页的 `sources.chat.enabled`。
操作者读完这段正确的解释，**能做的只有自己去别处翻**。

U14 把聊天搬成独立页时，我把"配置"留在了设置页、把"状态与解释"搬了过来，
**于是这一页变成只读的诊断书**。这是 U14 的遗漏，不是原设计。

---

## 2. 工作页：建立与删除的机制确实是反体验的

**核实结果：`projects` 与 `works` 只有 `GET` 与 `POST`，没有任何 `DELETE`/`PUT` 路由**
（`src/app/http.ts:382-391`）。也就是说：

- **建错了一个项目或工作，就永远删不掉**——面板上没有按钮，是因为**后端根本没有这个能力**。
- 建错了唯一的补救是"再建一个对的，然后无视那个错的"，而错的会一直留在列表里、
  一直出现在派活页的「归入工作」下拉里、一直被全局搜索搜到。
- 这不是 UI 呆板，是**能力缺口**：要修得动 `src/`（Engine 方法 + 路由 + 事务 + 测试），
  产物哈希会变，是这一轮里唯一需要碰后端的一项。

另外三个体验问题（纯前端可修）：

1. **建立路径要求先懂概念**：要建"工作"得先决定它属不属于"项目"，而项目与工作的区别只写在两段
   33/39 字的说明里。**没有"我就想归个类"的最短路径**。
2. **两个表单永远摊开**（见 1.3），列表与表单争同一屏。
3. **详情区默认是一句"选择左边一个项目或工作"**——落地即空，而列表只有一项时完全可以默认选中它。

---

## 3. 任务页「全部」：信息无差，没体现"全部"该有的功能

实测 12 行，每行的内容是：`标题 + done + session · operator + 1 天前 + 摘要前若干字`。问题：

1. **"全部"没有分组**：进行中的和已结束的混排成一个平面列表。而"全部"这一档的**本质功能**
   恰恰是"把两类放一起看"——那就该**分两段**（进行中 / 已结束），否则它和"进行中"档没有区别，
   只是多了噪声。
2. **已结束的任务看不出结局与原因**：行上只有一个 `done`（英文），而 `failed`/`stopped`
   与 `done` 在视觉上只差颜色；**结束原因（`ended.reason`）根本不在列表行上**，
   要逐个点进详情才知道"这张为什么停了"。
3. **看不出归在哪条流水**：行上没有工作名（只有详情里有），所以"这条流水最近几张都怎么样"
   在列表上答不出来——而这正是"工作"这个概念存在的理由。
4. **摘要与标题争位置**：摘要原文直接接在时间后面，长摘要把行撑得很高，
   12 行里每行都是"标题+英文+来源+时间+一大段摘要"，**扫读时找不到锚点**。
5. **"等你回答"只是一个文字标记**，没有和 U7 的徽标、总览的 KPI 用同一种视觉语言。

---

## 4. 记录页：两类东西挤在一页，而第二类被 359 字埋着

1. **判定与丢失是两件事**：判定是"门禁怎么判的"（每个请求都有），丢失是"队列放弃了什么"
   （异常才有）。U14 把它们放同一页是对的（都是"门与队列做了什么"），但**没有分区导航**，
   于是丢失那节要么被滚过去、要么用 359 字把自己顶到眼前。
2. **判定列表没有筛选**：14 条里想只看"被拒的"，只能靠眼睛扫颜色。
   而"谁被拒了、为什么"是这一页**唯一的实用问题**。
3. **结局与原因是英文**（见 1.1），且 `reasonText` 是服务器写给日志的句子，不是写给人的。
4. **忽略按钮的语义不清楚**：非 accept 的行有一个「忽略」按钮，但"忽略一条判定"是什么意思、
   点了之后会怎样，页面上没说（它其实是"我看过了，把它收起"）。

## 5. 派活页与聊天页的其余细节

**派活**
- 「一次性派 / 定时派」是两个 chip，但它们切换的是**完全不同的两套内容**（一套表单 / 一套列表+表单），
  视觉上却只是两个小胶囊——**切换的份量与控件的份量不匹配**。
- 「标识」是 id 的直译，而它旁边的 47 字解释其实是在说"这是排期的主键，改名会重算下次触发"。
  **名字该说清它是什么，而不是靠一段话补救。**
- 「范围」两个 textarea 的 placeholder 都是**空的**，而默认值（"只在自己的目录里工作"）只写在 label 里。
  留空会发生什么，得读 label 才知道。
- 配方下拉的说明"配方就是 examples/ 里那几个文件"——**`examples/` 是仓库里的路径**，
  对操作者没有意义；该说的是"选一个把标题、请求、范围填好，你再改"（这半句已经有了，前半句是噪声）。

**聊天**
- 顶部三个胶囊是 `受理模式 auto` / `allowedSenders operator` / `disabled`——**中英混排、且第三个只有一个词**。
  `disabled` 是这一页最重要的状态，却是三个胶囊里最不起眼的一个。
- 「回复计数」一节有 42 + 143 + 139 = **324 字**解释两个数字，而两个数字本身在总览与顶栏已经出现过。
  解释该收进折叠，数字该留。
- 频道与身份映射两个空表都写着"（0）"，**空表 + 长解释 + 摊开的表单**三者叠加，
  第一次来的人分不清"我该先做哪一件"。实际顺序是：**先启用来源 → 再加频道 → 再映射身份**，
  而页面是按"队列 / 频道 / 映射 / 计数"排的，**没有体现这个先后**。

## 6. 建议的修法（U17 系列，按"先解锁、再降噪、后重排"）

| 包 | 内容 | 是否碰后端 |
| --- | --- | --- |
| **U17** | **中文化三类枚举**：stage / outcome / 聊天状态胶囊，建立一张词表（`done`→已完成、`waiting`→等你回答、`accept`→已受理、`ignore`→已拒绝、`observe`→只记录…）；`reasonText` 保留原文但收进「技术细节」，人读的那一行改成中文 | 否 |
| **U18** | **解释一律收进折叠，状态与动作提前**：聊天 220 字、记录 359 字、回复计数 324 字全部改为"一句话状态 + 可展开的为什么"；每页第一个可见元素必须是**状态或动作**，不是段落 | 否 |
| **U19** | **就地给下一步**：聊天页顶部加「启用/停用这个来源」开关（写 `sources.chat.enabled`）；空频道时把"先启用→再加频道→再映射"做成**三步引导**（当前步骤高亮，已完成的打勾） | 否 |
| **U20** | **表单收进"新建"动作**：工作页两个表单、派活页排期表单改为按钮唤出（页内展开，不用原生弹窗）；工作页列表只有一项时**默认选中** | 否 |
| **U21** | **项目与工作的删除/归档**：Engine 方法 + 路由 + 事务 + 测试 + 面板两步确认。**唯一需要碰后端的一项**，产物哈希会变 | **是** |
| **U22** | **任务「全部」分两段**（进行中 / 已结束），已结束行**带上结局与结束原因**、带上所属工作名；摘要截断为一句并给「展开」 | 否 |
| **U23** | **记录页分区 + 筛选**：判定/丢失两个子页签（或锚点导航）；判定加"只看被拒"筛选；「忽略」按钮改名并说明后果 | 否 |
| **U24** | **派活页细节**：模式开关升级为更重的分段控件；「标识」改名为「排期代号」并把规则收进折叠；`范围` 的 placeholder 填上默认值原文；删掉 `examples/` 那句噪声 | 否 |

**顺序理由**：U17/U18 是"看不懂"与"无处下手"的直接解药，且**不动结构、风险最低**，先做能立刻改变观感；
U21 要碰后端（事务、级联、测试），放在观感问题解决之后单独做，避免一次改动里混两种风险。
