# 执行纪律

这份文档不是愿望清单。每条规则后面都跟着**这个仓库里真实发生过的事故**——规则是从事故里长出来的，
所以它写的是"当时做哪一步就能避免"，而不是"应该更小心"。

判断一个改动属于哪一档，看它**最坏情况下能破坏什么**，不是看它有多少行。

---

## 第 0 档：所有档位都适用的四条

这四条是本次事故的主要来源，所以放在分档之前。

### 0.1 绿灯的定义是退出码，不是输出里的一句话

**规则**：任何"通过 / 全绿 / 干净"的说法，必须由一条**我读了退出码**的命令产生。
`grep` 出来的 `Tests N passed` 不是绿灯；`| head -N` 之后的任何东西都不是绿灯。

**事故**：第 11–18 轮我反复报告"构建干净、567 条全绿"。实际上
(a) 我用 `| head -N` 截断输出，`head` 提前退出触发 SIGPIPE 杀掉上游，而 `build` 是 `check` 的最后一步——
**构建被静默杀掉了**，`lib/index.js` 陈旧 7.5 小时、盖的还是 schema 版本 1；
(b) `pnpm test` 在 567 条全过的同时报 **40 个未处理错误**，`pnpm check` 的**退出码一直是 1**。
两件事我都看不见，因为我从没读过退出码。（S32）

**做法**：`cmd > /tmp/x.log 2>&1; echo "退出码: $?"`，先看退出码再看内容。
管道里只要有 `head`，就假设上游可能被杀，用 `PIPESTATUS` 或先落盘。

### 0.2 声称之前先核产物，而不是核源码

**规则**：凡是"已落地 / 已部署 / 已生效"的说法，证据必须来自**将被使用的那个产物**，
不是来自我改过的那个源文件。

**事故**：同 S32。我说"构建干净"时，依据是源码 typecheck 通过；而宿加载的是 `lib/index.js`。
验收代理一条命令就戳穿了：`find src -name '*.ts' -newer lib/index.js` → **20 个文件**，
以及对产物 `grep -c` 那批新符号 → **全部为 0**。

**做法**：这类断言要变成测试，不要变成习惯。`tests/build.spec.ts` 现在断言
产物比每个源文件都新、盖的版本号等于 `SCHEMA_VERSION`、不再创建已删除的表——
它第一次运行就抓到了当时仍未重建的产物。**能被测试的纪律就不要靠自觉。**

#### 0.2 的补充：**产物新鲜度只覆盖进 bundle 的文件**

`scripts/gate.sh` 的新鲜度检查是 `find src tests -name '*.ts' -newer lib/index.js`，
它抓的是"源码改了而产物没重建"。**但有几类文件随包发布、运行时从磁盘读、却永远不进 `lib/index.js`**：
`panel/index.html`、`prompts/*.md`、`cordis.patch.yml`、`locale/*.json`、`examples/`、`README.md`
——即 `package.json` 的 `files` 数组里除 `lib` 之外的全部。

**对它们套用新鲜度规则是没有意义的**：它们本来就永远不进 bundle，"比 `lib/index.js` 新"只取决于编辑顺序，
而**一个会任意触发的检查会被忽略，那比没有检查更坏**。

**所以闸门改为报告它们的 sha256**（在计数行之后、结论之前，**只报告、不判定、不影响退出码**），
清单来源是 `package.json` 的 `files` 数组而不是硬编码路径——**否则下一个随包目录就是同一个盲区**。
输出按路径排序，**同一棵树两次运行逐字节相同**（已实测），所以可以直接和上次发布的清单 diff。
另有 `scripts/gate.sh --shipped-only`：只打印清单、四步一步都不跑、**且不碰 `/tmp/myagent-gate.log`**
（日志是唯一留痕的东西，清掉它就等于销毁别人上一次完整闸门的证据）。
**注意那个模式的退出码 0 只代表清单打印成功，不代表闸门通过**——判定权始终在完整闸门的退出码（0.1）。

这个盲区被实测过两次：第 46 轮改了 `panel/index.html` 而产物哈希不变；
0.1.2 改了 `prompts/worker.md`、**771 条测试全绿而产物哈希仍是 `3f772ddc…`**。

## 0.3 证据先于修复：不许按假设改第二次

**规则**：一个缺陷修了一次没好，**下一次动作必须是取证据，不是再改一版**。
在拿到能区分候选原因的那一项数据之前，不许再动代码。

**事故**：S31（inbox 归档重复）我先改成"先认领后归档"，12 次里仍失败 2 次；
我又准备改串行化闩。真正的进展来自把**判定证据埋进断言**——失败时打印每份副本的注解首行。
它一出来就证明两份副本都走了 `accepted` 分支，从而暴露出真因是**归档名用了时间戳而不是事件身份**
（重复的那次也走 `accepted` 分支，因为 `receive` 对重复 Trigger 返回的是已存的 disposition）。
前两次修改都"看起来对"，都不是解。

**做法**： intermittent 缺陷先做两件事——把断言改成**自诊断**（失败时说出实际值），
以及列出"什么观测能区分我的候选原因"。取到那个观测之前不改代码。
并且**不要**把测试改成宽容断言、也不要给它加重试：那只是把竞态藏起来。

### 0.4 修一类，先枚举这一类

**规则**：发现一个缺陷时，先问"这是哪一类的实例"，把这一类的**所有**实例找出来再动手。
修完一处就在文档里说清还剩几处，**不许写"已修"如果兄弟实例还在**。

**事故**：`rule` 成为第四种来源后，三处各自手写了三个 kind 的代码同时错了：
`sourcePolicy` 的三元链、`gate()` 里算 `enabled` 的**同一条**三元链、`authorizationShape.perSource` 的枚举。
我修了第一处，然后在文档里写"两个新旋钮都进 authorizationShape，所以都推动策略版本"——
**那句话是假的**，第三处根本没改。后果是收紧规则来源的授权不会推动策略版本，
没有任何在跑的 Ticket 会被告知。（S33）

同类事故还有两次：`health.record()` 在扫描末尾把**同一次扫描里刚记的告警**擦掉——
我在 cron 里修过一次，几轮之后在 `RuleSource` 里又写了一遍同样的 bug。

**做法**：`grep` 出这一类的全部实例（三元链、枚举、手写列表），一次改完；
更好的修法是**让它无法再漏**——派生而不是枚举（`settings.sources[kind]`、`Object.keys(...)`），
这样第五个成员不可能只被某个调用点看见。

### 0.5 失败的子代理不是死掉的子代理

**规则**：子代理"失败退出"之后，先查它的状态、先试着唤回它，**再**决定要不要从残件重建它的成果。
`inactive` 不等于不可继续——直接子代理在任何状态下都能收消息，会话上下文完整保留。

**事故**：第 19 轮的验收代理跑完了全部项目、做完了清理，但在写报告之前失败退出。
我看到"failed"就假定它脑子里的东西全没了，于是从 `/tmp` 的残件重建了报告，
并把三项标成"证据已丢失"（`assignment_stale` 是否真被抛出、三条负面路径的 Decision 措辞、停止后是否仍有写入）。
实际上 `list_agents` 显示它是 `inactive`——**一条消息就能问回来**。
我甚至没有先查状态就做了不可逆的选择（自己写报告），这恰好违反 0.3：
按假设行动，而不是先取那个能区分候选的观测。

**代价**：重建出来的报告只有"能从文件里读到的"，丢掉了它的判断与叙述——
哪些项目它认为只是部分验证、它实际跑的命令、它对负面路径的评估。
而且我写下的"证据已丢失"是**错的陈述**：证据没丢，是我没去要。

**做法**：子代理失败时，按这个顺序：`list_agents` 看状态 → 能发消息就把**具体的缺口清单**发给它
（不是"继续吧"，而是逐项问它还知道什么）→ 只有确认不可继续时才从残件重建。
唤回时要同时给它**新的边界**（别重跑已拆掉的环境、别碰别的代理正在改的文件、别重建产物），
否则它会去做已经做过或已经失效的事。

**同时要求它区分两种证据**："我记录下来的"与"我记得的"不是一回事，
报告里要标明每一条属于哪种——这比一个自信的答案有用。

### 0.6 离线验证不等于与生产无关：构建目录可能就是生产加载的那个

**规则**：跑构建之前先问"**谁在 link 这个目录**"。如果一个活着的宿主以 `link:` 装着这个包，
那么 `pnpm build` 就会**热重载它**——而重新挂载会触发 schema 迁移、重置内存态、重读设置。
验证性构建要么在副本目录里做，要么先告知操作者。

**事故**：第 20–28 轮我跑了约 6 次 `scripts/gate.sh`（它含 `pnpm build`）。
`myagent` 是以 `link:~/Documents/SA/myagent` 装进日常 profile 的，
所以**每一次构建都可能在操作者的日常宿主里热重载插件**。它在 05:33:53 真的重载了，
并把日常库从 schema 1 迁到了 5——而我此前对操作者说过两次"重载是你的决定"、"库仍是 version 1"。
详见 `00-audit-and-plan.md` 的 **S37**。

**这一条为什么单独立**：我已经有了第 4 档（固定版本、冻结变更、独立验收），
隔离验收也确实做对了（独立 profile / 端口 / stateDir）。漏的是**离线那一侧**——
我把"跑测试与构建"当成了与生产无关的动作，而它写的是生产正在加载的那个文件。
**判据不是"我改的是不是生产代码"，而是"我写的这个文件有没有活着的进程在读"。**

### 0.7 委派要拆小：一个大子代理会让所有其它环节排队

**规则**：一个子代理 = **一个交付物、一个文件、一个长度上限**。任务书里必须写明四件事：
唯一的产物是什么、不许碰什么、**先落盘再完善**、以及汇报不超过几行。

**判据**：如果一个任务的产出需要"读遍整个仓库"，它至少要按目录或按交付物拆开。
"顺手把 A 和 B 都写了"不是一个小任务，是两个。

**事故（两次，同一个原因）**：
- 验收代理跑了几小时、跑完了全部项目、做完了清理，然后**在写报告之前失败退出**——
  叙述全丢。我能重建出 90% 只是因为它的**残件在磁盘上**（`/tmp/myagent-acceptance-v2/` 里的
  evidence JSON 与 worker 日志）。它自己的判断与措辞没了，而我因此把三条结论写错了（见 02b 的更正）。
- 面板代理串行跑了几个小时，**我全程只能等**——期间我本来可以并行推进三份文档。

**所以三条具体要求**：
1. **先落盘，增量写**。任务书里要明说："先用真实的章节标题把文件建出来，再逐段填"。
   一个磁盘上的半成品，比一个永远没落地的完整品有价值得多。
2. **中间证据写磁盘，不要只留在对话里**。这条是上一轮唯一救回我的东西：
   残件在，就能重建；残件不在，"证据已丢失"就成了真的。
3. **汇报限行数**（≤ 8–10 行）。不限行数的汇报会把子代理的整个上下文倒回来，
   而主代理的上下文才是最稀缺的资源。

**拆分之后要做的两件事**：给每个子代理划清**文件边界**（不同代理不得同时改同一个文件——
本项目里 `panel/index.html` 与 `tests/panel.spec.ts` 曾经只有一个所有者，这条守住了），
以及**告诉正在跑的那个代理它的范围缩小了**，否则它会继续做已经被别人接走的部分。

**主代理的责任不因拆分而减少**：接口契约、集成、验收仍然是主代理的。
拆小是为了并行与失败可恢复，不是为了把判断也拆出去。

### 0.8 变异检验保持绿色时，先怀疑测试

**规则**：变异检验的意义是"证明这条测试能失败"。所以撤掉修复后测试**仍然是绿的**，
第一反应必须是**测试太弱**（扰动没有可观测后果），而不是"代码本来就没问题"。

**事故**：第 36 轮 P8 的 C1，变异是"把 `Date.now()` 混进回复文件名的 key"——**最初绿的**，
因为两次投递落在**同一毫秒**，那个时间戳根本没有机会显现。
实现者没有收手，而是把测试加强到两次投递间隔 5ms（并写明理由：效果队列的重试在退避之后，
绝不会在同一瞬间发生），之后变异**变红**。

**与 0.3 的关系**：0.3 说"第二次修之前先取证据"，这一条是它在测试侧的镜像——
**"绿"是一个需要被解释的观测，不是一个结论**。同一族还有第 25 轮那次：
测试助手 `one()` 永远返回 `tickets[0]`，于是"两张 Ticket 互相读产物"的测试实际在测
"一张 Ticket 读自己的产物"，而它**通过了**。两者都表现为绿，而绿都不意味着对。

**做法**：每条新测试都要变异检验；变异不红就**改测试直到它红**，
而不是把这条变异记成"已检验"。

### 0.9 钉子要在交给别人的那一刻量，不能从早先的记录里抄

**规则**：任何"版本钉子"（产物哈希、schema 版本、依赖版本）在**交给另一个执行者的那一刻**必须重新测量，
不能从文档里早先的记录复制。抄来的钉子是对**一棵已经不存在的树**的断言。

**事故**：第 36 轮我把 P8 任务 C2 的基线产物写成 `f07e56a6017318e0…`，那是 `00-audit §4.32` 里记的值。
而 C2 开工时实测是 `4a6bb032372e3cc2…`（276275 字节，比前者多 **7 字节**）——
差的是**我自己**在这中间对 `src/core/errors.ts` 的一次措辞修改。
它自己量了才发现，所以没有一条结论被污染；**如果它信了我的数字，就会把一个正确的产物当成"被谁改过了"**，
或者反过来把一个真被改过的产物当成正常。

**同一族的另一处**：我在 §4.33 写下"产物哈希与基线逐字相同，因为 `chat.ts` 零导入者、没进 bundle"。
这句话在 C1 汇报的那一刻为真，**在我改完 `errors.ts` 之后就不真了**。
它依据的**判据**仍然成立（新模块落地后哈希不变 ⇒ 它没进 bundle ⇒ 未接入），
但我引用的**那个实例**过期了。**判据与实例要分开保存**：判据可以长期引用，实例必须带时间戳。

**做法**：交钉子时附上"我在什么时刻、用什么命令量的"；
以及**构建的确定性要先证明**（C2 连构建两次得到同一哈希），否则钉子本身就没有意义——
一次无变更的重建就会让验收的钉子失效。

### 0.2b 变异检验之后、钉住产物之前，要重建一次

**规则**：变异检验会把源文件还原，而**还原会更新它的 mtime**。于是产物虽然内容与源码一致，
`build.spec` 的新鲜度断言仍然会红——**看起来像"源码改了没构建"，实际上是"构建过之后又还原了"**。

**事故（两次，同一个原因）**：第 33 轮与第 37 轮，都在变异检验之后发现"有一个源文件比 `lib/index.js` 新"。
第 37 轮那次差点让我把一个正确的钉子当成可疑的交出去。

**做法**：变异检验结束后**跑一次完整闸门**（它会重建），确认
①退出码 0、②`find src tests -name '*.ts' -newer lib/index.js` **为空**、
③**重建前后的哈希相同**（内容确实没变，且构建是确定的）。三条都成立，那个哈希才可以当钉子交给别人。
本项目已两次验证构建是确定的（同样的源码 → 同样的 sha256），所以"哈希不变"本身就是"内容未变"的证据。

### 0.10 "列举已知取值 + else 兜底"是一个会到期偿还的债

**规则**：任何对**封闭联合类型**做分派的地方，要么写成**穷尽**的（TypeScript 的 `never` 检查会替你盯着），
要么让兜底分支**大声失败**（记一行健康问题、点名那个没人处理的状态），
**绝不能让兜底分支静默地把新成员当成某个旧成员处理**。

**为什么**：联合类型长出新成员时，穷尽写法会在编译期报错，大声兜底会在运行期报警，
而**静默兜底什么都不会说**——它只是把新值归档到旧值的位置上，而所有测试都还是绿的。

**这一族在本项目已经出现四次**：
1. **S33**：三处 fallthrough（`sourcePolicy` 的 ternary、`gate()` 的 `enabled`、`authorizationShape.perSource`）。
   症状包括"停用 session 会静默停用 rule"，以及**审计记录里的一句假话**
   （拒绝理由说 rule 未启用，而它其实启用了）。
2. **`signatureOf` 的第三处**：`rule` 读的是 session 块，于是两个来源共用一个签名。
3. **`enabled` 的第四处**：cron/inbox/session 各自硬编码了 `enabled`，后加入的 kind 只出现在派生条目里、
   而那里不带 `enabled`，于是停用 rule/chat **不移动 `policyVersion`**，而旁边的注释声称覆盖了每一个。
4. **第 44 轮**：`receive` 把已存的 `lost` 行当作 `{stored:'duplicate'}` 返回（**与事实相反**），
   而这个值流进三个 Source 的 catch-all（`inbox.ts:228-234`、`chat.ts:385-386`、`cron.ts:194-196`），
   把任何未点名的处置状态归档为 accepted/ignored。

**第 1–3 次的修法是同一个**：把"列举 kind"改成**从数据派生**（`settings.sources[kind]`、`sourceKinds(settings)`）。
派生不会忘，因为它是算出来的；列举会忘，因为它是一份清单。
**一句值得贴在墙上的话：一份 kind 的清单，就是一份"会被忘掉的东西"的清单。**

**第 4 次剩下的部分（未修，规格已写）**：那三处 catch-all 今天对 `lost` 不可达
（只有 `rule.ts:99` 入队 `trigger` 效果，而规则来源从不调 `receive`），而且 `receive` 的修复让它们保持不可达。
但**任何未来的 `Disposition` 成员都会走进它们**。修法是让兜底大声：
把隐式的"else → accepted"换成显式的 else，**记一行健康问题、点名那个状态**，
并把它计入一个诚实的计数（不是 `accepted`）——归档目录同理，
因为把一个没被受理的请求归档进 `accepted/` 是**目录在说一句假话**，而目录是操作者会去看的。

## 第 1 档：简单、局部、可逆 → 直接执行，快速验证

**判据**：改动范围在一个模块内；不改任何被别处依赖的形状；错了可以一次性撤掉；不碰持久化数据。

**纪律**：
- 改完立刻跑**最小**验证（该模块的测试 + typecheck），不要攒着一起验。
- **读原文再改**。本会话里大量时间浪费在补丁锚点没命中（`!! x0`）上：
  我凭记忆写锚点，而文件里是 `]).refine` 不是 `}).refine`、是 `engine.require` 不是 `engine.ticket`、
  是 `refusal` 不是 `failure`。**先 `grep` 出准确原文，再改。**
- 改完**核对改动落地了**：`grep -c` 新符号、或 typecheck。本会话出现过两次
  "脚本打印成功、磁盘没变"和一次"重复键把我自己的记录器覆盖了"
  （对象字面量里写了两个 `enqueue`，后一个把前一个吃掉）。
- **不留死代码**。删掉因改动而无人调用的东西（如 `unlinkSafe`）；
  也不要新加一个已有守卫的副本（我在 `executor.launch` 里加过一条 `liveTicket` 检查，
  而它上面 45 行就有一条更完整的）。

**验证标准**：该模块测试通过 + typecheck 通过 + 我读了退出码。

## 第 2 档：跨模块、有接口依赖 → 先定义契约，再分工实现

**判据**：改动跨两个以上模块；引入或修改一个端口/接口；有并行工作（子代理）会依赖这个形状。

**纪律**：
- **先写契约，再写实现**：接口签名、每个方法的前置条件、失败时的语义（抛错 / 返回空 / 记录）。
  契约里必须写明**谁在什么时刻调用它**，否则实现方会猜。
- **端口改了，所有实现同时改**。`Repositories` 加一个成员，`Store` 与 `Memory` 都要实现；
  `ToolsHost` 加一个成员，**测试 harness 里的字面量也要加**，而且桩要**忠实**：
  `attempt(ticketId)` 返回 `undefined` 会让测试只走回退路径、永远碰不到身份本身。
  本会话两次踩到（`artifacts`、`attempt`）。
- **一个缺陷有两个实现时，写一份对两个实现跑同样断言的契约测试**。
  `tests/transaction.spec.ts` 就是这么来的：`Memory` 与 `Store` 的事务语义曾经四处分歧，
  而所有领域测试都跑在 `Memory` 上，于是套件绿着、生产错着。
  这份测试的价值靠**变异检验**证明：把 `Memory` 改回旧行为，嵌套回滚那条立刻变红而 `Store` 那组仍绿。
- **子代理并行时，主代理拥有接口**。不同子代理不得同时改同一个核心文件；
  它们报告缺陷，主代理决定修法（验收代理就是这么用的：它只写报告与 /tmp，
  两个策略缺陷由我修，然后我给它新的钉住哈希）。

**验证标准**：契约测试对每个实现都跑；typecheck 覆盖所有实现（包括测试里的桩）。

## 第 3 档：涉及状态机、持久化、安全 → 先审计现状、定义不变量与失败条件，再实施

**判据**：改状态转换；改 schema 或任何落盘格式；改授权、门禁、权限、沙箱。

**纪律**：
- **先审计，写下不变量与失败条件，再动手**。本项目的 `docs/v2/00-audit-and-plan.md` 就是这个产物
  （S1–S34 结构性发现、D1–D11 架构决定、能力五态清单）。它的价值在事后被反复证明：
  级联取消能做，是因为 S8（事件必须在提交后发布）先修了；
  等待用 `Later` 表达而不是 effect 失败，是因为审计先写下了那条规则。
- **改契约之前先量爆炸半径**。S11 的修法必须**分两步且顺序不能反**：
  先让测试的假执行器像真执行器那样把尝试标成 running（提高 harness 保真度），
  再收紧 `report()` 只接受 running 的尝试。反过来做会得到十几条红测试，
  而"测试全红"会被误读成"修复错了"。**这个顺序本身是先审计出来的。**
- **持久化改动必须可回滚，而且回滚要演练过**。
  `scripts/verify-migration.sh` 在**副本**上跑迁移并演练回滚，线上库自始至终只读；
  每一步 schema 变更都必须在真实数据的副本上拿到"既存数据逐字节未变"的证据。
  两个教训写进了脚本注释：摘要要用**显式列名**（`select *` 量的是形状不是数据，
  一次加列会让它误判成"数据被改动"）；打开静止的 WAL 库要 `immutable=1`
  （否则这个工具在它被造出来要保护的那种文件上失败——S34）。
- **安全断言不许含糊**。逻辑守卫不是强安全边界；不得伪造 token 统计；
  不得把"平台身份"映射成一个假的 actor。放行系统 actor 是**系统第一次能授权没人要求的工作**，
  所以它是一个设置，而且是**两道关**（开关 + 那个身份在名单上被点名），不是一道。
- **失败必须可见**。不可见的失败是这个项目最贵的一类缺陷：
  prepare 失败的 Ticket 曾经无报告、无 attention、无通知、不可重试（B2）；
  主 Session 缺失时所有前台回报被静默丢弃而健康板干净（B1）。
  新增任何"悄悄返回"的路径都要问：操作者从哪里能看见它发生了？

**验证标准**：不变量有测试；关键状态转换有测试；迁移在真实数据副本上演练过；
新测试经过**变异检验**（撤掉修复就变红）——本会话对 S19、S12、S11、S8、级联都做过。

## 第 4 档：涉及集成与生产环境 → 固定版本、冻结变更、独立验收

**判据**：真宿主、真端口、真状态目录；或者任何"别人正在验证的东西"。

**纪律**：
- **钉住产物身份**：sha256 + 字节数 + 构建时间 + "没有源文件比它新"。
  验收报告里的每一条结论都绑定到这个身份。上一轮验收代理就是这么做的，
  所以它能在我改源码的同时给出仍然有效的证据。
- **冻结变更**：验收运行期间**不重建产物、不改它要验证的源码**。
  本轮我先修完两个缺陷、重建一次、再把最终哈希交给代理，而不是让它对着一个会在中途变掉的产物跑。
  如果必须在验收期间改代码，就要重新验收，并说清哪些结论作废。
- **独立环境**：独立 profile、独立端口、独立 stateDir。
  绝不碰日常宿主的 stateDir 与 profile；绝不调用 `plugin_manager`；对日常宿主最多只发 GET。
- **前后快照，证明没碰**：对不该被改的目录做 `stat` + `sha256` 快照并 `diff`，
  差异必须为空；共享文件若被写过（如为了构造不可运行的 Session 而归档一个 worker），要**恢复并证明恢复了**。
- **收尾要验证**：后台作业全部 killed、端口已释放、锁文件已消失、`-wal`/`-shm` 已归位。
  本轮还加了一条：**停止之后核对是否仍有写入**（mtime 与 sha256 在一分钟后不变），
  因为 S32 那个"定时器在库关闭后触发"的缺陷如果在生产里成立，就会长这个样子。
- **验收代理只报告、不修复**。它发现缺陷时给出可复现的证据与严重度，
  由主代理决定修法——否则两个代理会同时改同一个核心文件，而集成责任就没人负了。

**验证标准**：验收报告里每条能力标五种状态之一（真宿主验证 / 离线验证 / 部分实现 / 仅有设计 / 尚未实现），
并且**明确区分"我通过真宿主驱动了它"与"它只有离线覆盖"**。
本轮就有两条只能标后者：`createProject`/`attachWork`/`dependOn` 在 `src/` 里**零调用者**，
没有任何 HTTP 入口能驱动它们——这种话必须写出来，不能让"有测试"读起来像"能用"。

## 0.13 子 Agent 回来之后，核对哈希，不要读汇报

**事故（工程第 1 轮）**：一个被允许临时变异 `src/app/sessions.ts` 的子 Agent 死在中途，
**把那条提权修复留在了退回状态**——`decorateAgent` 回到 `decorate(agent, this.host.ticket(ticketId))`，
修复标记 grep 命中 0。它没有说谎，它**什么都没说**。

**救回来靠的是它动手前写下的两样东西**：变异前的 sha256 全值、以及一个备份文件。

**规矩**：

1. **派单时要求代理在动手前把目标文件的 sha256 全值写进笔记第一段**，并先做备份
2. **每一波代理结束后，主 Agent 先核对那些哈希，再做任何其它工作**——包括在代理"成功"返回时
3. **凡"改坏再还原"的操作，还原后必须比对哈希**，不能只看"我 cp 回来了"

**为什么**：变异检验的定义就是"临时把代码改坏"，而**"临时"依赖于一个还活着的执行者去还原**。
**一个死掉的执行者留下的是一个永久变异。** 0.2b 是这条规矩在构建产物上的版本，0.13 是它在源码上的版本。

**推论**：给子 Agent 的边界里，**能不改 `src/` 就不给**；必须给的时候，
把"变异—还原"限定为**单文件、有备份、有哈希记录**，并且**要求它在笔记里逐次登记变异与还原**。


### 0.13 的补充：**"代理已失败"不等于"代理已停止写入"**

工程第 2 轮的实测：一个子 Agent 报告失败之后，我在两条相邻命令里量到
`src/app/sessions.ts` 的两个不同哈希（`20c475fa…` → `120a7888…`），而期间没有任何代理应该在跑。
最可能的解释是**那个进程在报告失败之后仍在收尾**——它的笔记里最后一处变异写着
"Restored, `shasum -c` OK"，而我第一次测量正好撞在它自己的变异状态上。

**我当时的判断是"S44 修复又丢了"，而实际是量到了一个中途状态。**

**规矩**：
1. 代理报告失败之后，**先确认树是静止的再测量**——最简单的办法是**同一份哈希连量两次**，
   或等一小段时间再量；不一致就说明还有人在写
2. 一个标记 grep 命中 0，**在树的静止性未确认之前不构成"修复丢了"的证据**
   （这次就是：同一个标记在下一条命令里命中 1）
3. 结论只能建立在**静止之后**的测量上。**这与 0.3 是同一条规矩在并发场景下的形式：
   先让被观察的东西停下来，再读它。**
