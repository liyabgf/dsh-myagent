## 二、遍历扫描：方向要求、但接口没打通的

判据：README「方向」三句话（聊天优先 / 减少人的负担 / 诚实优先）＋ SECURITY 的安全模型，
逐条问"这个方向要走通，系统里缺哪根线"。**方向明说不做的（Assessor 模型评审、多租户）不列为缺口。**

### G-1（扫描的最高优先）：聊天侧没有"查账面"——方向说聊天优先，可关于过去的工作，聊天一问三不知

- **方向依据**：方向第一句"聊天优先：每加一个功能先问能不能在聊天里完成"。
- **现状证据**：前台工具共 9 个（`src/app/tools.ts` 的 `mainTools`：create / list / status / answer / note /
  reply / stop / close / retry）——**全是"管进行中的任务"**。没有任何工具能：列一张已完成任务的**产物**、
  查它的**血缘**（用了谁、被谁用）、按标题或时间**召回**过去的工作、看某个「工作」下有哪些任务。
- **负担后果**：操作者在 Telegram 里问"上次那份 csv 叫什么来着"，前台只能回答"我有个工具查不了，你去开面板"——
  这正是方向禁止的：把人从聊天室赶到面板里。
- **最小打通**：前台加一个只读工具 `myagent_recall`（按关键词/时间窗搜历史任务，返回标题、状态、产物清单、
  血缘计数与工作归属；上限如 10 条、每条摘要 160 字，与产物目录同一套节流常数）。
  读侧无新增写路径，风险集中在"别把不该泄的东西（路径前缀之外）报出来"。
- **次级（同一族）**：聊天侧也无法把任务归入工作/项目（面板独占）。列在面板计划里一起权衡。

### G-2：桥死了没人知道——聊天是唯一日常来路，而它的存活没有任何信号

- **方向依据**：聊天优先 ⇒ 桥是系统的**主动脉**；"需要人的事推到你面前"。
- **现状证据**：`src/sources/chat.ts:558-566`——健康只报**积压**（`unhandled/` 里的文件数）。桥进程死了的表现是
  **没有新消息**，积压不变、健康全绿、面板照常。launchd 会拉起它，但 launchd 不在的时候（手动跑、单元写错、
  token 被吊销后桥每轮报错退出）系统侧完全沉默。
- **最小打通**：桥每轮循环写一个**心跳文件**（mtime 即可，`bridges/lib/run.mjs` 里一行）；chat source 每个 pass
  检查各频道目录的心跳年龄，超过 `2×pollMs` 之外的阈值（比如 5 分钟）就上健康板一条"channel X 的桥 5 分钟没心跳"。
  零新概念：复用现有的 per-channel 健康条目。

### G-3：真隔离的接口只封了两个洞——方向写着"真隔离是方向"，`ExecutionSandbox` 名不副实

- **方向依据**：README「不做什么」第一条明说现状无沙箱、方向是真隔离；`docs/v2/12 §3.1` 已列六处直接 IO。
- **现状证据**：接口抽象了两个动作；附件投递、`RESULT.md`/`REPLY-UNDELIVERED.md`、删除时目录清理、
  目录列举与度量、`prepare` 命令执行（其 cwd 是宿主路径）仍走宿主直连。**接口存在≠边界封住**。
- **最小打通**：六处逐个搬进接口（每处一个洞一次提交），`'vm'` 才从"诚实地说做不到"变成"可以做"。
  这是 P-1/P-2/P-3 的上游：物化配额、完整 id 目录名都应该发生在沙箱接口内而不是绕过它。

### G-4：手艺"未经复核"标注得很诚实，但**复核这件事根本做不了**——正文就在 API 响应里，面板不渲染

- **方向依据**：方向第三句"诚实优先"；`SECURITY.md` §5 说"判断要不要暂停它的依据是没人复核过"。
- **现状证据**：`SavedSkill` 自带 `content` 全文（`src/app/prompts.ts:57`），`GET prompts` 原样返回（`http.ts:634`）；
  面板的手艺卡只有标题、说明、来源、暂停、两步删除——**没有"看正文"**。一个想复核的操作者只能去开 SQLite。
- **最小打通**：面板手艺卡加「查看正文」抽屉（数据已在响应里，纯前端工作）＋从正文跳来源任务。
  归入面板计划 P0；在此记录是因为它是"接口通了、消费者没接上"的典型——**打通的最后一步永远在界面上**。

### G-5：worker 静默卡死默认**不可见**——"推到你面前"的承诺有个默认关闭的例外

- **方向依据**：方向第二句"必须问的只问一次"、以及 delivery 的"等人一定会被推到该看到的人面前"。
- **现状证据**：`src/core/policy.ts:239`——`watchdog.silentMs` 默认 **0 = 关**。一个 worker turn 静默挂住
  （模型流卡死、工具不返回）时，除非操作者自己开面板看"进行中"，没有任何东西告诉他。
- **待操作者定（这是默认值的产品决定，不是技术缺口）**：默认开（如 30 分钟）会不会太吵？
  或者保持 0，但在面板总览的"进行中"卡上加"最老一张已经跑了 X 小时"的提示线。

### G-6：面板全部中文硬编码，而 bundle 明明带着 locale 机制

- **现状证据**：`panel/index.html` 无任何 `t()`/locale 机制（grep 零命中），同时 `locale/en.json`/`zh.json`
  在宿主侧服务工具描述。单操作者、中文用户——**这不是缺口，是待定**：记录于此，等"要不要给英文用户"成为
  真问题再动。方向上优先级最低。

### G-7：面板是纯轮询（5 秒全量 state、详情页 3 秒）——功能越长越重

- **现状证据**：`panel/index.html:4168`（5s 全量）、`:1112`（3s 详情）。已经做了按 tab 排除（settings/prompts/new
  不参与 5s 轮询）。**暂不推 SSE/WebSocket**：宿主 webServer 的注册模型面向请求-响应，推送要新通道；
  先做"按 tab 定向刷新 + 只在当前 tab 可见时轮询"（document.hidden 时停表），收益大、风险小。

## 五、三个新桥：企微 / QQ 官方机器人 / 钉钉（操作者点名加入）

共同工作量（每个桥都有，照 `bridges/telegram/` 的形状）：`bridges/<name>/{bridge,transform}.mjs` +
README 与环境变量表（`tests/bridges.spec.ts` 的文档漂移双向断言自动覆盖新目录）、面板「聊天」页的平台清单行与
引导正文（launchd/systemd 单元模板）、`identities` 映射复用、出站分片与退避复用 `bridges/lib/`。
**凭据依旧不进 myagent 设置**（桥自己的 env 文件）——这条不变量对三个新桥同样成立。

差异在**入站架构**，这决定了可行性排序（以下为待调研确认的判断，不是结论）：

| 桥 | 出站 | 入站 | 硬骨头 |
| --- | --- | --- | --- |
| 钉钉 | 群机器人 webhook | 企业内部应用 **Stream 模式**（websocket 长连接，**无需公网回调**） | 应用资质与权限点；Stream SDK 或裸 ws 的取舍 |
| QQ 官方机器人 | 官方 API | 官方 **websocket 网关**（无需公网回调） | intents/消息格式/频率限制细节多；群聊与频道权限分级 |
| 企微 | 群机器人 webhook（只能发） | 自建应用**回调 URL**（需公网 HTTPS）或会话存档（资质/付费） | **myagent 的 webServer 是 loopback，回调进不来**——要么给桥一个公网入口（隧道/反代），要么只做"出站+人工触发"，要么会话存档。这是三个里唯一可能"打通不了双向"的 |

> 所以顺序是 **钉钉 → QQ → 企微**，且企微开工前先做一轮协议调研并给出"双向 / 仅出站 / 不做"的三选一结论，
> 不把调研成本摊到实现里。每个桥独立成一个小工程：调研 → transform → bridge → 面板行 → 漂移测试 → README，
> 各自一次发布，不捆在一起。

## 六、每日技术演进侦察任务（`evolution-scout-daily`，每日 09:00）需要什么

活体核实：排期已建（`daily 09:00 Asia/Shanghai`，enabled），**尚未触发过**（triggers 里只有旧排期的记录）。
提示词本身质量很高（60 分钟硬上限、防投毒八条、对着 myagent 真代码分析、"没有就明说没有"）。
但它对系统的要求有五条**现在不成立**：

| # | 需求 | 现状证据 | 最小打通 |
| --- | --- | --- | --- |
| S-1 | **60 分钟墙钟预算，且子任务不能绕过** | 全仓无 `maxRuntime/wallClock/deadlineMs/timeBudget`（grep 0 命中）——上限目前只是提示词里的一句话；而子代理**不受 `tools.guard` 约束**（已知缺口），"不得用子任务绕过"在系统层无人执行 | 排期/任务级 `maxRuntimeMs`：到点由 runtime 打断并记 `interrupted`（复用 watchdog 的打断机制）；子代理计入父任务的预算（`background.ts` 已有 children 清单，缺的是"预算归属"） |
| S-2 | **结果要送到操作者每天看的地方** | cron 触发的任务没有 `replyTo`，报告只落 `RESULT.md` + 主 Session 通知——**不进 Telegram**。侦察提案会安静地躺在面板里 | 排期加可选 `deliverTo`（channel+thread），delivery 用它当回程地址；或全局 `sources.cron.deliverTo` 兜底 |
| S-3 | **跨天记忆：今天的侦察要能站在昨天的侦察上** | 每次触发是新 Ticket、新上下文；跨任务复用要求同 Work 或双方未归组（cron 任务未归组，**能读**但只能靠产物目录自己找） | 同一排期的历次运行自动归入同一个 Work（名取排期 name）——与现有三条自动归组路径同族，去重规则现成 |
| S-4 | **不可信来源任务应有更窄的工具面** | worker 预设全系统只有一种（含 `bash`）；防投毒八条全是提示词级 | 新增只读变体预设（`myagent-worker-readonly`：去 `bash/pwsh/write/edit`，留 web/read/grep），排期可指定 `preset` |
| S-5 | 提案要登记成产物，明天才引用得到 | 提示词没要求 `myagent_report files:[…]` | **零代码**：提示词加一行"把当日提案写成 proposal-<日期>.md 并随报告登记" |

S-5 先做（一行提示词），S-2/S-3 是"侦察结果有人看、看得连续"的前提，S-1 是"60 分钟是真的"的前提，
S-4 是防投毒从"嘱咐"变"边界"的那一步。**在 S-1/S-2 打通前让侦察任务真跑，等于让它在一个没有预算、
没有人收信的岗位上值班。**

阶段 3 · **让侦察任务真正上岗**（S-5 → S-2 → S-3 → S-1 → S-4，按此序：先零代码，再送达，再记忆，再预算，再工具面）

阶段 4 · **聊天查账面 + 桥的心跳 + 面板 B 组**（G-1 `myagent_recall`、G-2 心跳、B-⑤血缘图、B-⑥频道健康卡、B-⑦行内归组）
  出口：关于过去的工作，聊天里问得到；主动脉通不通一眼可见。

阶段 5 · **三个新桥**（钉钉 → QQ → 企微；企微先出调研结论再定做不做双向）
  出口：每桥一次独立发布，漂移测试与面板引导齐备。

阶段 6 · **长期线**（G-3 真隔离六处搬接口、P-4 随包收窄、面板 C 组、G-6/G-7）
  出口：`executor.sandbox: 'vm'` 从"诚实说做不到"变成"可以做"。

**贯穿纪律不变**：每阶段结束跑四步闸门（退出码判据）+ 真浏览器（跳过项显式登记）+ 变异含强形式 +
发布前隐私扫描 + 公开仓只经 release 管道或干净增量 + 每轮在 00 记档。阶段之间不捆发布。
