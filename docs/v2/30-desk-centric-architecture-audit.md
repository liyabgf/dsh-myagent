# 总管中心架构审核报告

**审核时刻**：2026-11-11 16:35（Asia/Shanghai）
**审核定位**：总管是唯一交互入口，所有事情先经总管，总管调动 DSH 功能分配任务、监视执行、处理中间问题。

## 一、总管应该做什么

按你的定位，总管必须能完成以下闭环：

```
操作者 → [消息] → 总管（判断）→ 分派任务（建票/自答/提问/丢弃）
                        ↑                    ↓
                        ← [report] ← worker 执行 → [结果] → 总管审视 → 回复操作者
```

| 职责 | 总管能做吗 | 怎么做 |
|------|-----------|--------|
| **接收消息** | ✅ | relay/inject 把消息送进主会话 |
| **判断请求** | ✅ | 模型推理（纯文本，不需要工具） |
| **自答** | ✅ | `myagent_close_ticket(state: 'ready')` |
| **丢弃非请求** | ✅ | `myagent_close_ticket(state: 'dropped')` |
| **开任务票** | ✅ | `myagent_create_ticket` |
| **向操作者提问** | ✅ | `myagent_close_ticket(state: 'blocked')` 或 `myagent_reply` |
| **查任务列表** | ✅ | `myagent_list_tickets` |
| **查任务详情** | ✅ | `myagent_ticket_status` |
| **向 worker 发指令** | ✅ | `myagent_answer_ticket` |
| **给 worker 补充信息** | ✅ | `myagent_note_ticket` |
| **停止任务** | ✅ | `myagent_stop_ticket` |
| **重试任务** | ✅ | `myagent_retry_ticket` |
| **提出决断** | ✅ | `myagent_raise_decision` |
| **检索记忆** | ✅ | `myagent_recall` |
| **回复请求者** | ✅ | `myagent_reply` |

**结论：工具面完整。** 总管有 11 个工具，覆盖了你描述的全部职责。

## 二、结构审核：总管能看到什么、被通知什么

### 总管被唤醒的时机

| 事件 | 唤醒方式 | 总管能知道吗 |
|------|---------|------------|
| 新 chat 消息进 triage | `relay`（队列投递，唤醒 turn） | ✅ **主动唤醒** |
| worker 报告 `blocked`/`waiting` | `relay`（队列投递，唤醒 turn） | ✅ **主动唤醒** |
| worker 报告 `ready`/`failed`/`dropped` | `notify`（注入历史，不唤醒） | ⚠️ **被动注入，不唤醒** |
| worker 报告 `progress` | `notify`（注入前 120 字摘要） | ⚠️ **被动注入，不唤醒** |
| worker 发 `ask_desk` | `relay`（队列投递，唤醒 turn） | ✅ **主动唤醒** |
| Watchdog 超预算/升级 | `relay`（escalation） | ✅ **主动唤醒** |
| 策略变更 | `notify` | ⚠️ **被动注入** |

### 结构问题

**问题1：`ready`/`failed`/`dropped` 不唤醒总管**

worker 完成了任务（`ready`），总管只收到一条 `notify`（注入历史、不唤醒 turn）。按你的定位"总管监视执行、审视结果、回复操作者"——**总管应该在任务完成后主动审视结果**，而不是被动地等历史积累。

当前设计：`ready` 直接发给请求者（聊天室/面板），总管只是"被通知了"。总管没有机会审视结果质量、决定是否需要追加说明或调整。

**问题2：`progress` 不唤醒总管**

worker 每次报告进度时，总管只收到一条 120 字的注入摘要。按你的定位"总管监视执行情况"——**总管应该能主动查看进度并做出调整**。当前总管没有"定时查看"机制，只能被动接收注入。

**问题3：没有"总管主动巡检"机制**

总管只在被 relay 唤醒时才有 turn。没有"每 N 分钟检查一次所有运行中票"的定时器。按你的定位"监视查看任务执行情况进行调整"——这需要总管有**主动巡检**能力，不依赖 worker 汇报。

## 三、结构审核：总管的可靠性

### 单点故障

| 单点 | 故障时发生什么 | 有降级吗 |
|------|--------------|---------|
| 主会话（Session）损坏 | **所有 chat 消息卡死**——triage 进了但执行不了 | ❌ 无降级 |
| 主会话工具桥故障 | **总管判断对了但落地不了**——不能建票/关票/答题 | ❌ 无降级 |
| 主会话 ID 被删 | **effects 指向不存在的 Session**——launch 失败 | ❌ 无自动恢复 |
| DSH 重启 | 主会话恢复或重建，但历史可能丢失 | ⚠️ 部分恢复 |

### 当前实际故障

**主会话 `session-051e3501` 的工具桥从 11-09 开始持续故障**。错误是 PTC 模式的 `projectToolSchema` 抛错，导致主会话**所有工具调用**（含原生 `bash`）全部失效。

- 我删除了损坏的 Session → 新 Session 不工作（effects 指向旧 ID）
- DSH 重启 → 新 Session 创建但 relay 消息没投递到它
- **总管从 11-09 到现在（16:35 北京，约 3 天）完全无法执行任何工具**

### 结构缺口

**缺口1：没有 triage 降级路径**

当 triage（主会话工具桥）不可用时，chat 消息应该**跳过 triage 直接建 worker 票**。当前没有这个降级——triage 票进来后卡在"总管不能执行工具"的状态。

**缺口2：没有主会话健康检查**

总管 Session 的工具桥是否可用，没有任何检测机制。故障从 11-09 持续到今天，面板显示 0 红线（因为健康板只查"Session 是否存在"，不查"工具是否可用"）。

**缺口3：没有主会话自动重建**

主会话损坏时，应该能检测到并自动销毁+重建。当前完全靠人工发现+手动删。

## 四、结构审核：总管与 worker 的协作

### 当前协作路径

```
chat 消息 → triage 票 → 总管判断 → myagent_create_ticket → worker 票 → worker 执行
                                                                       ↓
                                                                  report → notify 总管
                                                                  blocked → relay 总管
                                                                  ask_desk → relay 总管
                                                                       ↓
                                                                  总管 → answer/note/stop/retry
```

### 结构问题

**问题4：worker 的 `failed` 不触发总管审视**

worker 报告 `failed` 时，总管只收到 `notify`（注入历史，不唤醒）。但按你的定位，总管应该**审视失败原因、决定是重试、调整还是向你提交**。当前 `failed` 的处理是：直接发给请求者 + 注入总管历史。总管不会被唤醒来审视。

**问题5：worker 的 `ready` 结果总管无审视**

worker 报告 `ready` 时，结果直接发给请求者（聊天室），总管只收到 `notify`。按你的定位，总管应该**审视结果、决定是否直接发还是先检查再发**。当前是"worker 自己发，总管事后知道"。

## 五、修复建议（按优先级）

### P0：加 triage 降级——工具桥不可用时跳过 triage

**改动**：在 `executor.ts` 的 triage launch 路径加一个超时/失败检测：如果 relay 在 N 秒内没有响应（或者总管报告 `failed`），**回退到直接建 worker 票**。

**效果**：即使主会话完全损坏，chat 消息仍然能建票执行，不会卡死。

### P1：让 `ready`/`failed` 唤醒总管

**改动**：把 `ready`/`failed`/`dropped` 从 `notify`（注入）改为 `relay`（唤醒），让总管在任务结束时有 turn 来审视结果。

**效果**：总管能在 worker 完成后审视结果质量，决定是否需要追加说明、调整或直接转发。

### P2：加总管主动巡检

**改动**：在 runtime 的 pass 里加一个"N 分钟没有 relay 但有 running 票"的触发器，让总管主动 `list_tickets` + `ticket_status` 巡检。

**效果**：总管不依赖 worker 汇报也能知道执行情况。

### P3：加主会话健康检查

**改动**：在 watchdog 里加一个"主会话工具桥可用性检测"——周期性地让总管执行一个轻量工具调用（如 `myagent_list_tickets`），失败 N 次就自动销毁+重建 Session。

**效果**：工具桥故障不再需要人工发现和手动修复。

## 六、总结

**工具面完整**：总管有 11 个工具覆盖全部职责。

**结构缺三个机制**：
1. **降级**：总管坏了不回退到直接建票
2. **审视**：任务结束/失败不唤醒总管审视
3. **巡检**：总管没有主动查看执行情况的定时器

**可靠性缺两个机制**：
1. **健康检查**：不检测总管工具桥是否可用
2. **自动重建**：主会话损坏不自动销毁+重建

这五个机制是从"chat 消息进来后总管能可靠地判断、分派、监视、审视、回复"这条闭环里缺的。
