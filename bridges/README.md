# 平台桥（bridges/）

把一个聊天平台接成 myagent 的一条**来源**。桥是一个独立的小程序：一头连平台（收消息、发回信），
一头把消息写成**频道目录里的 `.md` 文件**。myagent 只认文件，所以**换平台不用改 myagent 一行代码**。

```
平台  ──(桥)──►  频道目录/msg-<id>.md  ──(chat Source)──►  门禁 ──► 任务 ──► worker
平台  ◄──(桥)──  频道目录/out/reply-<hash>.md  ◄──────────────  报告
```

- 契约的实现与理由：`src/sources/chat.ts` 的文件头注释（那是规范本体，本文是它的操作者视角）
- 设计与生态节点定位：`docs/v2/25-ecosystem-nodes-and-task-environment.md`

---

## 1. 桥只做三件事

1. 把平台事件**写成入站 `.md`**
2. **消费 `out/`** 并发回平台
3. 保管自己的凭据与重连

**桥绝不做**：身份判定（那是 `sources.chat.identities`）、授权（那是 `allowedSenders`）、
去重（那是 Trigger id 的纯函数性质）、重试（那是效果队列）。

> 把安全判断放进桥，等于把它放进一个**没有测试、没有门禁、没有面板**的进程。
> 桥是运输，不是裁判。

---

## 2. 入站：一个文件 = 一条消息

频道目录**顶层**的一个 `*.md`。子目录（`out/`、`accepted/`、`observed/`、`rejected/`、`unhandled/`）都是
Source 自己的；**点号开头的文件一律被跳过**（桥的临时文件与状态文件都用点号开头，因此对 Source 不可见）。

```md
---
from: U01ABCDEF        # 平台身份，必填：它是 sources.chat.identities 的键
id: msg-123            # 平台消息 id，可选；没有它则**文件名**就是这条消息的身份
thread: t-9            # 可选；会随 replyTo.thread 回到出站文件
title: weekly alerts   # 可选；文件名是兜底
---
正文即请求文本
```

解析规则（照抄 `parseMessage`，写桥前请对着它核一遍）：

| 规则 | 后果 |
| --- | --- |
| 文件必须以 `---` 开头，闭合栅栏是其后的第一个 `\n---` | 不满足就是"没有 front matter"，整篇当正文 |
| 每行按 `/^\s*([A-Za-z][\w-]*)\s*:\s*(.*)$/` 切，键**转小写** | 值里可以有冒号（只有第一个冒号参与切分） |
| 值 `.trim()` 后**只剥一层首尾引号**，**不做反斜杠反转义** | **所以要净化，不要转义**：写 `\"` 会把反斜杠留在值里 |
| 值是**单行**的 | 值里的换行必须替换成空格，否则尾巴会被丢掉 |
| `from` 为空 / front matter 坏了 | **不是错误**：像未映射一样**留住**，就地改好、下次扫描受理 |

**四条硬性质**：

- **身份只映射、不推断**。`from` 不在 `identities` 里 → **不产生 Trigger，也不产生 Decision**，文件**原地留着**，
  健康板报"有几条等着映射"。留住是**唯一可逆**的答案：门禁拒绝会把 Trigger 存成 `ignored`，
  而 Trigger id 是消息的纯函数，于是那条消息**再也不能被重新评估**——即使你后来加了映射。
- **幂等**。Trigger id = `key('chat', channelId, messageId)`，**只由消息身份决定，绝不含时间戳**。
  重投同一个 `id` 是同一条消息；真要新消息必须换 `id` 或换文件名。
- **先认领后处理**。取走一条消息时**先 unlink 原文件**，两次重叠扫描只有一个能归档。
  所以桥**不要**用"文件还在"判断是否已处理。
- **原子写**。Source 会读顶层每一个 `*.md`，所以桥必须**先写点号临时文件再 rename**
  （`lib/inbound.mjs` 已经这么做）。半截文件被读到，就会变成一条没有 `from` 的消息永远滞留。

**其它上限**：单条消息 **> 512 KiB 会被拒**并归档到 `rejected/`（这样的消息永远不可能被受理，
留在目录里只会一直占位）。

## 3. 出站：`out/reply-<hash>.md`

- 内容 = 可选 front matter `---\nthread: <t>\n---\n` + 正文
- 文件名 hash 是 `(channel, thread, text)` 的**纯函数** → **重试写同样字节，不会重复发**
- 放在 `out/` 而不是与入站文件并列：Source 会读顶层所有 `*.md`，回信放外面会被当成一条没有 `from` 的消息**永远滞留**
- `deliver` **故意不受** `enabled`/`paused`/`deny` 约束：那三者拦的是**进气**（不产生新工作），
  而一份已授权工作欠下的报告不是新工作。扣住它会让"答案没送到"与"答案本来就不欠"无法区分
- 频道不存在或被停用 → `reply_unroutable`（"地址写过了，却没人收"）

**桥必须消费 `out/`**：读走 → 发到平台 → **发送成功后**移到 `out/sent/`。
`lib/outbound.mjs` 的三条保证：

1. **at-least-once**：发送失败就把文件**留在原地**，下次再试。宁可重发，不可静默丢答案。
2. **不重复发**：`out/sent/` 里已有同名文件就跳过。myagent 的重试会写同样字节，
   所以"同一个文件名"就是"同一封回信"——这是去重键。
3. **不无界增长**：`sent/` 里超过 `MYAGENT_REPLY_KEEP_DAYS`（默认 7 天）的会被清理。

## 4. 套件（`bridges/lib/`）

| 模块 | 职责 | 关键性质 |
| --- | --- | --- |
| `frontmatter.mjs` | 读写消息文件的 front matter | **净化而不是转义**；解析器与 Source 逐条对齐 |
| `inbound.mjs` | 写入站 `.md` | 文件名是**消息身份的纯函数**（掺时间戳＝一条消息变两个 Trigger）；点号临时文件 + rename |
| `outbound.mjs` | 消费 `out/` | 见上三条保证 |
| `state.mjs` | 游标持久化 | `.bridge-state.json`（点号开头，Source 扫不到）；坏了就从头开始，而不是拒绝启动 |
| `log.mjs` | 结构化单行 JSON | 桥无人值守跑在 launchd/systemd 下，事后唯一的动作就是 grep |
| `run.mjs` | 轮询 + 退避 + 优雅退出 + 心跳 | 退避是因为"每秒失败 20 次"在平台侧看起来像攻击，可能导致**凭据被吊销** |

**依赖策略**：套件与 Telegram 桥**零运行时依赖**（Node ≥18 自带 `fetch`）。
**飞书桥是唯一的例外**，因为它的长连接是 **protobuf over WebSocket**——零依赖意味着手写一个
**没人能从文档核实的协议**，那正是桥最不该有的性质。它的依赖关在 `bridges/lark/package.json` 里，
不污染 myagent。

## 5. 加一个新平台

1. **抄 `bridges/telegram/`**：`transform.mjs`（纯映射，可测）+ `bridge.mjs`（入口）。
   **纯映射必须拆出来**——入口文件在 import 时就读环境并启动循环，留在里面的东西**一样都测不了**。
2. 映射时回答这五个问题（每一个都有一条测试对应）：
   - **`from` 用哪个 id？** 一个平台常有好几个 id（飞书就有 `open_id`/`union_id`/`user_id`）。
     **选一个并永远用它**：混用会让同一个人在 `identities` 里变成两个身份，而操作者看不出为什么其中一个不灵了。
   - **消息 id 全局唯一吗？** 不唯一就**加前缀**（Telegram 的 `message_id` 只在单 chat 内唯一，
     所以写 `<chatId>-<messageId>`；不加前缀会让两个群的同号消息**塌成同一个 Trigger**，
     而因为 Trigger id 是纯函数，第二个群的消息会被**静默去重掉**）。
   - **`thread` 用哪个字段？** 用"这一串的根"，不要用"直接上级"
     （飞书的 `parent_id` 是直接上级，回它会让答复**每轮再嵌一层**）。
   - **@ 怎么判定？** 优先用平台给的实体（entities/mentions），**不要**用子串猜。
     并且检查平台是否有"省略 mentions 数组"的已知行为（飞书就有）。
   - **什么消息该跳过？** 没有发送者的（频道广播）**跳过而不是留住**——留住是给"还没映射的人"的答案，
     而广播根本没有"人"可映射，留住等于在健康板上永久留一个谁也解决不了的条目。
3. **回信路由**：回复文件只带 `thread`、不带会话 id（契约是平台无关的），
   所以桥自己维护 `thread → 会话 id` 与 `defaultChat`，存在 `.bridge-state.json` 里。
4. **加契约测试**（`tests/bridges.spec.ts`）：合成事件 → 断言映射结果与跳过原因；
   以及**用真 Source 跑一遍双向**（见 `tests/chat.spec.ts` 的 "a platform bridge on the other end of this contract"）。
   > 只用自己的 helper 造文件、再自己读回来，**只能证明 Source 与它自己一致**。
   > 两个独立实现互相印证，才叫契约测试。
5. **写一份 `<平台>/README.md`**：从零到收到第一条回信，加一份操作者验收清单。

## 6. 排障

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 发了消息，**一秒内**没反应 | Source 有 **1 秒稳定窗口**（`SETTLE_MS`，防止读到写了一半的文件） | 不是故障。最多等 1 秒 + 一个轮询间隔 |
| 面板「等映射」有数，消息不动 | `from` 不在 `sources.chat.identities` 里——**这是设计**，留住是可逆的 | 在面板「聊天」页把那个平台 id 映射成一个人，下次扫描就受理 |
| 面板「待取回信」长期非零 | **桥没在跑**：myagent 已写完答案，没人来取 | 起桥；看它的日志有没有崩溃 |
| 日志里 `reply_unroutable` | 频道被删了或被停用了，而回信地址已经写下 | 恢复频道，或接受这封回信送不到（它仍在 `out/`） |
| 消息进了 `rejected/` | 超过 512 KiB，或门禁拒了 | 看文件里的 annotation；拒绝是不可逆的（Trigger id 是纯函数） |
| 消息进了 `unhandled/` | 判定状态是 Source 不处理的那一类 | 健康板会报积压数；这是要修代码的信号，不是配置问题 |
| 群里说话它不理 | 默认 `mentions` 模式：群里**只认 @ 它的消息** | 要全收就设 `*_MODE=all`（先确认群里的人都在映射表里） |
| 同一条消息变成两张任务 | 桥把时间戳掺进了文件名或 `id` | 文件名与 `id` 必须是**消息身份的纯函数** |
| **终端里手动跑正常，当守护进程就失败** | launchd/systemd **不读 `.zprofile`**：代理的 `NODE_EXTRA_CA_CERTS`、`PATH` 都不在 | 把它们写进 env 文件；日志里看 `causeCode`（例如 `SELF_SIGNED_CERT_IN_CHAIN`） |
| 桥每秒报错、越报越快 | 平台在限流，而桥在猛敲 | `run.mjs` 会退避到最多 60 秒；持续失败说明凭据或权限有问题 |

## 7. 安全边界

- **凭据不进 myagent 的设置文档**：`channels` 与 `identities` 都是 `.strict()` schema，
  塞不进额外字段——这不是限制，是边界。面板的高级 JSON 区会**把整份 settings 渲染出来**，
  写进去的 token 就等于画在屏幕上。凭据放 env 文件（`chmod 600`），守护单元只**引用**它。
- **三层授权不要混**：`identities` 决定**你是谁**，`allowedSenders` 决定**谁能派活**，`scope` 决定**能干什么**。
- **提示注入是真实风险**：群消息不由你写。一个新桥接进来之前，先想清楚"群里任何人都能让它做什么"。
  缓解：`observe` 模式先跑一周、收紧 `allowedSenders`、给任务写明确的 `scope`、
  以及**不要让桥所在的机器登录敏感账号**。

## 8. 测试与验收的边界

**离线可测**（`tests/bridges.spec.ts`，35 条）：字节级的 front matter、净化规则、幂等、原子性、
at-least-once、去重、两个平台的映射与每一种跳过原因。

**离线可测且最值钱**（`tests/chat.spec.ts`）：**桥套件写 → 真 `ChatSource` 读 → 出现 Trigger**，
再 **Source 写回信 → 桥套件消费 → 拿到 thread 与正文**。

**必须真机验收**（每个平台一次，需要你自己的凭据，我代替不了）：见各平台 README 的验收清单。
**在真机验收之前，不要认为一个桥"能用"**——离线测试证明的是契约，不是平台。
