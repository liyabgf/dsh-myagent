## 状态判定依据

状态列只取五值：**真宿主验证 / 离线验证 / 部分实现 / 仅有设计 / 尚未实现**。判定时遵守三条：

1. **更正块优先于原报告。** `02-live-acceptance-v2.md` 是代理失败退出后从残件重建的，其中三条结论被
   `02b` 推翻：Watchdog 的"通过"应为"探测得证、救援被证伪"；"rescued 在 launched 之前所以是救援导致启动"
   是错的因果（那个 launch 是 `sleep 90` 自己睡完的）；"两张规则票都跑到 done"只有一张成立。
   本文按更正后的版本标注。
2. **线上结论绑定产物身份。** `02b` 开头写明：一切线上结论只适用于 `lib/index.js` sha256 `f6b29adc…`，
   不适用于当前 `src/`。本次 GET 探测进一步确认日常宿主加载的 bundle **早于第 25–28 轮**：
   `GET /api/tickets/:id/progress` 的返回里**没有 `usage` 键**（第 26 轮才加），
   而 `projects`/`works`/`dependencies`/`events` 四条路由都返回 200（第 21–22 轮加的）。
   已加载 bundle 的 sha256 无法从外部读到（没有路由暴露它），那一点标 **未核实**。
3. **"有测试"不等于"能用"，也不等于"改到了生产"。** 零调用者的引擎命令标离线验证并注明入口状态；
   只在 `src/` 里、尚未进入日常宿主 bundle 的改动不标真宿主验证。

## 迁移后果汇总

对既有数据，按"操作者需要做什么"排序：

1. **日常库已经在 version 5，而且不是按计划升的**（S37）。单向门已过：旧构建再挂上来会 `SchemaTooNew`
   拒绝打开、插件静默什么都不做。既存数据本身完好（计数与演练一致、`integrity_check ok`、四张数据表逐字节未变）。
   真要回滚是"改版本号 + 装回旧构建"或"恢复备份"二选一，**代码与 schema 版本必须一起回滚**（`03` §4.3）。
2. **今后每一次在这个目录里构建，都可能再次热重载日常宿主**（纪律 0.6）。验证性构建要么在副本目录里做，
   要么先告知操作者。这是一个**持续存在**的危险，不是一次性事故。
3. **设置文档是降级的硬阻塞，而 `SCHEMA_VERSION` 管不到它**。V2 加的设置键全部可选/带默认值，
   所以升级方向安全；但降级到不认识新键的旧构建时，**新键会让旧构建解析失败** → Runtime 构造抛错 →
   插件挂载不上，而目录看起来完全健康。那一行 kv **就是操作者的排期数据**。降级前必须把新块删掉。
4. **V1 的全局暂停永久销毁了暂停期间的请求**（S9）。没有 Trigger 可以恢复、cron 槽位永不重放、
   inbox 文件已在 `rejected/` 且再投字节相同的文件会撞上重复短路。这部分数据**在 V1 下就已经丢了**，V2 不能追回。
   同理：V1 下停用来源一周等于丢掉那一周的所有 cron 槽位（游标被擦），也不可恢复。
5. **不回填的四类**：事件日志（既存 Ticket 的历史从建表那一刻才开始）、产物登记（日常库 `artifacts = 0`）、
   依赖边（既有 Ticket 没有边）、prepare 失败被结束的 Ticket（保持结束、`reports` 仍为空、仍不可重试）。
   这是刻意的分阶段施工，不是遗漏。
6. **`key('assignment', ticketId, ordinal)` 没有改**，所以两个并发 Assignment 仍然会撞键——
   多 Worker 并发（P3 的主体）在数据模型上还不可能。改它等于改变所有已存 Ticket 的形状。
7. **inbox 归档名新旧混存**：既有 `accepted/` 里的时间戳命名文件不改名，新归档用 `<triggerId>-<原名>`。
8. **worker 仍然没有沙箱**（S1 未修，`WORKER_PERMISSION = 'danger-full-access'`）。
   Ticket 的 `scope` 是提示词约束，不是控制；Project/Work 是**分组不是隔离边界**（它们限制产物读取与协作通道的
   可达性，不限制 shell）。升级不改变这一点，风险清单只是把它写清楚了。
