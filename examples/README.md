# 两个可以直接用的配方

这两份是**验收用例**，不是演示：它们写的就是无人值守跑起来以后每天真正会发生的事，所以每一条都包含
「产出什么、放在哪里、怎样算做完、什么时候该 blocked」。`tests/recipes.spec.ts` 会用真实的 schema 和真实的
门禁校验它们，配方失效时测试会红。

## 1. 每日竞品摘要（定时）

`daily-digest.json` 是一份**完整的设置文档**，直接粘到面板「设置」页的文本框里保存即可。

它做的事：每天 09:00（Asia/Shanghai）抓四个源，只留最近 7 天的条目，和 `~/Documents/SA/digests/`
下最近一份对比去掉重复，写出 `TODAY.md` 和 `latest.md`，然后汇报 `ready`。

两个要点：

- **`acceptMode` 出厂是 `observe`**。第一天它只会记录「本来会派什么活」，一个 worker 都不会起。
  去面板「门禁记录」看一眼那条 `observed`，确认标题、范围、请求文本都对，再把 `acceptMode` 改成 `auto`。
- **成品目录是共享的**（`~/Documents/SA/digests/`），因为每日摘要必须能读到昨天那份。
  每个 Ticket 仍然有自己的目录做临时工作，`scope` 里把两个目录都写明了。如果你不想让 worker 写自己目录以外，
  就把 `scope` 改成只允许本目录，并用 `executor.prepare` 把昨天的摘要复制进来。

改源、改时间、改产出，都在面板「排期」页做（有下次触发预览），不必手写 JSON。

## 2. 月度数据报表（投递到收件目录）

`data-report.md` 是一个**请求文件**，复制到收件目录就会变成一张 Ticket：

```bash
cp examples/data-report.md ~/.dsh/state/myagent/inbox/
```

（收件目录以面板顶部「状态」气泡里显示的 `inbox` 为准。）

开头的 `---` 块是 front matter，只认两个字段：

| 字段 | 作用 |
| --- | --- |
| `title` | Ticket 标题；不写就用文件名 |
| `scope` | 这次工作能走多远；不写就用默认（只在自己的目录里工作） |

`---` 之后的正文就是 worker 收到的请求。文件被接手后会移到 `accepted/`，被门禁拒绝的移到 `rejected/`
并在文件头写明原因——所以「投了没反应」永远能在文件系统里查到原因，不会静默消失。

这份配方读 `~/Documents/SA/data/` 下的 csv，产出 `report.md`、`scripts/`（可复核的脚本）和 `charts/`。
把路径改成你自己的数据目录即可。

## 写配方的三条规矩

1. **当成写给一个不能反问你的同事。** 产出什么文件、放在哪里、怎样算做完，都要写死。
2. **把失败也写清楚。** 抓不到源、目录是空的、口径有歧义——分别该汇报 `failed` / `dropped` / `blocked`，
   以及 `summary` 里要说明什么。不写的话，worker 会自己编一个理由，而你无法判断它是不是真的做完了。
3. **`blocked` 只问一个问题**，并给出你建议的选项。一个问题能被一句话回答，三个问题不会。
